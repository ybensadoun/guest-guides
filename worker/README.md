# Guide worker

Builds guides that hosts have published. It runs on this computer, only while it is on and the worker is running. Before going public it moves to a small server: plan in `docs/plan-worker-on-server.md`, image in `worker/Dockerfile` (see "On a server" below).

## One-time setup
1. In Supabase: project `dmoxszfwulolqkgxtxcp` > Project Settings > API Keys > copy the **secret** key (starts with `sb_secret_`, or the `service_role` key). It can do everything in the database, so it stays on this computer only.
2. Create the file `worker/.env.local` (it is git-ignored) with one line:
   `SUPABASE_SERVICE_KEY=<paste the key here>`
3. Needed on this computer: Node 18+, Python 3 with Pillow and NumPy (`pip3 install pillow numpy`), and `npm install` done once in the repo.

Optional lines in `worker/.env.local`:
- `RESEARCH=cli` research nearby markets, things to do and emergency contacts, and translate, using the `claude` command on this computer (default `skip`: the guide is built from the host's answers only). Jobs from the editor (Find more, translate, automatic events) use the `claude` command unless `RESEARCH=api`.
- `RESEARCH=api` the same with the Claude API (web search and web fetch run on Anthropic's side) and the worker's own key `WORKER_ANTHROPIC_KEY=<key>`: for a server, where nobody is logged in to `claude`. Needs `npm ci --prefix worker` once (the Claude SDK). Optional: `RESEARCH_MODEL` (default `claude-opus-5-5`), `TRANSLATE_MODEL` (default `claude-haiku-5-5`), `RESEARCH_EFFORT` (default `medium`), `RESEARCH_MAX_SEARCHES` (web searches per request, default 20), `RESEARCH_USD_PER_DAY` (the worker stops asking Claude past this expected cost until the next day, default 5). Each Claude call writes its searches, tokens and expected cost to the log. These settings have their own names on purpose: Claude Code sets `ANTHROPIC_BASE_URL`, `CLAUDE_EFFORT` and others in its sessions.
- `HEARTBEAT_URL=<address>` a monitoring service's ping address, called at most once a minute while the worker runs (an alert when it stops).
- `AUTO_PUBLISH=0` hold built guides for review (status `ready`) instead of publishing them at once (default: publish at once, for the test phase).
- `POLL_SECONDS=10` how often to look for new guides.
- `OPENAI_API_KEY=<key>` switches on artistic covers (the `cover-art` job below). Without it the host sees "Artistic covers are not switched on yet."

## Run
Since 28 Oct 2026, 22:15, the worker runs on the server (Hetzner CX23 `guide-worker`, its address in `~/.ssh/config` on Yohann's Mac, see "On a server" below), not on the Mac: never start one on the Mac while the server's runs.
- Log: `ssh guide-worker 'cd /opt/guest-guides && docker compose -f worker/compose.yaml logs -f --tail 50 worker'` (`ssh guide-worker` works from Yohann's Mac: `~/.ssh/config`).
- Restart: `ssh guide-worker 'cd /opt/guest-guides && docker compose -f worker/compose.yaml restart worker'` (lets running jobs finish first, up to 15 minutes). Keys and settings: `/etc/guide-worker.env` on the server (root only), then `docker compose -f worker/compose.yaml up -d --force-recreate`.
- Updates: a push to `main` reaches the server within 5 minutes (`worker/server-update.sh`, timer `guide-worker-update`; `journalctl -u guide-worker-update` shows each one).

The Mac's launch agent (`worker/autostart.sh`) was the stopgap until the server and was removed on 28 Oct; the script stays until about 25 Nov 2026 as a fallback (server down for long: stop the server's worker first, then `sh worker/autostart.sh install` on the Mac). `status`, `restart`, `remove` work as before.

Only one worker runs at a time: a copy started by hand while another runs on the same computer says so and stops (a second one would put the first one's running jobs back in the queue). By hand, after `remove`: `caffeinate -i node worker/guide-worker.mjs`, `Ctrl+C` stops it. A guide or editor job left half-built when the worker stopped goes back in the queue as soon as it starts again (and after 30 minutes if a build stalls while the worker runs).

Build what is queued right now and stop: `node worker/guide-worker.mjs --once`

Try one "Find more" search without the queue (safe next to a running worker: it prints the suggestions and writes nothing): `node worker/guide-worker.mjs --find find-todo --slug <slug>` (or `find-markets`, `find-events`; `--out <file>` saves the whole result). With `RESEARCH=api` it shows what the search cost.

A stop by SIGTERM (a server's update or restart) takes nothing new and lets running jobs and a build finish before the worker exits; a second SIGTERM or `Ctrl+C` stops at once.

## On a server
`worker/Dockerfile` (build from the repo folder: `docker build -f worker/Dockerfile -t guide-worker .`) holds Node, Python with the generator's packages, the engine and the worker, with `RESEARCH=api`. No keys in the image: they come from the server's environment (`worker/compose.yaml` reads `/etc/guide-worker.env`); `worker/server-update.sh` pulls and rebuilds after each push. Only one worker may run: stop the one on the Mac before starting the server's. Plan, hosting options and setup steps: `docs/plan-worker-on-server.md`. The server's env file also sets `TZ=Europe/Madrid`, so the log shows local times.

## What Claude costs (since 29 Oct 2026)
With `RESEARCH=api`, every answer's expected cost goes into the database (`events`, kind `claude_cost`: budget, USD, model, searches, tokens). `RESEARCH_USD_PER_DAY` (default 5) adds up today's (UTC) before each question, so a restart or a push does not start the day again at zero. Each budget counts its own (`RESEARCH_BUDGET`): `daily` for the worker and the one-off commands, `monthly` for the monthly run (`worker/monthly.mjs` sets it, with `MONTHLY_USD`, default 30). Today's cost: `select sum((data->>'usd')::numeric) from events where kind = 'claude_cost' and data->>'budget' = 'daily' and created_at >= date_trunc('day', now() at time zone 'utc') at time zone 'utc';`

## Research of the area, before the build (29 Oct 2026, `../docs/plan-fast-builder.md` step 8)
In two stages, so publishing is quick and a visitor without an account costs little (Yohann: the few nearest first, the rest once there is an account):
1. At the listing link, with or without an account: a quick search (`area_research`, `runArea`) for the wow and the phone: the 5 markets nearest the house, whatever their distance (a city has them a few streets away, the countryside 10 to 20 km), and the emergency services, with at most 8 and 6 web searches, both at once (about a minute; measured in Barcelona on 29 Oct, one after the other: 0.43 USD, 106 s). Things to do come from Google in the swipe deck. The browser asks the database (`start_area_research`): one per area, shared for 14 days with every house within half the distance of the farthest market it found (`reach_km`: about 1 km in a city, much further in the countryside; one still being done is shared within 1 km), at most 2 a day per visitor, 4 per network address and 15 in all (change them in that function). `VISITOR_USD_PER_DAY` (default 3 USD, Claude API only) caps what these cost each day; past it, a row is left to the build (`limited`). Rows older than 30 days are removed.
2. Once the guide has an account (at once for a host who is signed in): the full research in the background, the guide job `research` (`researchJob`, at most one a day per guide): all the markets in reach and the things to do, the build's own questions.
The build (`areaResearch`, `mergeQuick`) uses the full research, adds the markets the quick search found that it does not have, takes the emergency services from the quick one, waits for either while it is still being done (up to 10 minutes) and only searches what is missing; if all else fails, the guide has the 5 nearest markets at least. Measured on 29 Oct 2026 before the two stages, one full research of Tordera cost 2.30 USD (markets 1.28, things to do 0.80, emergency 0.22) and took 8.5 minutes. Try one queued quick search without the queue: `node worker/guide-worker.mjs --area-research <id>`.

## What it does for each queued guide
1. Takes it (status `generating`) and writes progress messages the host sees.
2. Runs `engine/scripts/generate-site.py` on the host's answers (and research and translation when `RESEARCH=cli` or `api`), then the content check.
3. Uploads the images to the `guide-assets` bucket and saves content and theme to the guide row.
4. Sets status `published` (or `ready`), or `failed` with a plain message the host sees.

The guide is then at `https://porta-guides.netlify.app/g/<slug>`.

## Photos of deleted houses
The database cannot delete files, so the worker removes every `guide-assets` folder whose house no longer exists (a host deleted it, or their account): at start, then at most once an hour (`worker/sweep-photos.mjs`). Folders are listed before the houses, only folders named like a house id count, an empty list of houses stops it, and each house is checked again just before its photos go.

## Jobs from the editor (`guide_jobs`)
- `find-transport` (Getting around > Add a train station or bus stop, or Refresh the lines; params `{id, mode, name, lat, lng}`): Claude looks up on the web the lines through that station or stop (names and official colours), up to 5 places guests reach from it with the usual journey time, the timetable link and the operator; they are translated and written into the draft's station (`badges`, `to`, `link`, `auto`), and back in the job for the open editor. The host's own words (`tag`, `what`) and a timetable link they set are never touched. One lookup measured on 29 Oct 2026 (El Vendrell, Opus 5.5 with web search): about 1 minute, 0.40 USD. At most 20 a day per guide. Try one, written nowhere: `node worker/guide-worker.mjs --find find-transport --slug <slug> --station <id>`.
Up to three run side by side (each mostly waits for Claude), even while a guide is being built; two jobs that write the same guide (translate, auto-events) never run together. A search takes about 3 to 6 minutes. Run one worker at a time: when it starts, jobs left "running" by the previous one go back in the queue and start again.
- `translate`: fills the missing languages of the draft (or makes a draft from the live guide); the texts also go back in the job's `result` for the editor that is open.
- `find-todo`, `find-markets`, `find-events` ("Find more" on those steps): Claude searches the web around the house with the build's research rules plus the curation rule, leaves out what the guide has, checks each place on Google (`worker/places.mjs`, same rules as the monthly check: permanently closed ones are dropped, listing link, Google id and hours added; events are not checked), translates into the guide's languages and returns the suggestions in `result`. Nothing goes into the guide here: the host keeps or skips each one in the editor. At most 8 searches per guide a day. Needs `GOOGLE_PLACES_KEY` in `Guest Guides/.env` for the Google check (without it the suggestions are unchecked). "Find more" on Events looks at the next three months.
- `auto-events` (the host switches on "Keep events up to date", or presses "Search now"): the same search as the monthly run below, for one guide, written straight into the guide.
- `cover-art` ("Do it for me" or "With my own words" under Cover picture, in the editor and in the onboarding): OpenAI's image edit (`gpt-image-2.5-sunburst` since 28 Oct 2026, after OpenAI shut `gpt-image-1` down; `OPENAI_IMAGE_MODEL=<model>` in `.env.local` picks another one; 1536x1024, medium quality, about 0.02 USD each by OpenAI's token prices (one measured on 28 Oct: 1078 tokens in, 343 out, 23 s), the worker log shows the tokens of each drawing) redraws the chosen photo, by default as a Bauhaus-style artwork in the photo's own colours. `params.source` must be the guide's own storage or an Airbnb photo (a0.muscache.com); at most 8 a day per guide. The picture goes to `<guide id>/covers/art-<stamp>.jpg` and its path to the job's `result`; nothing changes in the guide until the host presses "Use this cover".

## Host's favourite places
Before the generator runs, each place the host typed (a name or a Google Maps link, answers.favEat) is looked up on Google near the house (`hostPlace` in worker/places.mjs, key GOOGLE_PLACES_KEY): position, distance, town, hours, kind, Maps link and Google id go into the job's `src/geocode.json`, which the generator reads. The host's own name stays. A place Google does not know keeps the host's words but gets no distance and no pin (`nomap`).

## Host images
When the host publishes, the onboarding sends their own images (logo, cover, photos, inspiration images) to the guide's storage folder (`<guide id>/host/`) and lists them in `answers._uploads` (an artistic cover the host kept is already in `<guide id>/covers/`). The worker downloads them into the job's `src/uploads` and `src/assets` for the generator. Without a logo the guide shows none; the icons then come from the house photo.

## Automatic events: `npm run refresh-events -- --apply`
For every published guide whose events file has `auto.on` (settings `skip`, `want`, `removed`, `reach`, saved by the editor with the `set_events_auto` database function). How far (`reach`, the editor's "How guests get around"): by car, every event within 10 km of the house however small, and only the main ones (each event's `scale`: regional or major) further out, up to the guide's radius; in a city, small ones within 2 km and the main ones within 8 km. Automatic events that do not fit are removed (older ones get their size asked once); the host's own events are never touched. Find more for events follows the same rule. Searches the next three months around the house: one general search that first works out the area's own traditions and where their dates are published (castells in Catalonia, Semana Santa and ferias in Andalusia...), and side by side one focused search per topic the host wants (up to three, up to 20 events each), with the host's topics to look for and to skip (any language: Claude reads them as topics, and the skip topics are also checked in English on what it found), translates, then in the live guide and in the host's draft: adds new events marked `"auto": true`, updates the dates of automatic events, drops automatic events whose dates have all passed. The host's own events are never touched; deleted automatic events (`removed`) never come back. Without `--apply` it reports what it would change. `--slug <slug>` for one guide. Run by the monthly task.


## The monthly run: `node worker/monthly.mjs`
On the server, the timer `guide-worker-monthly` (worker/systemd) runs it on the 1st of each month at 9:00 (Madrid), in its own container beside the worker: `check-guides --apply`, `--refresh-events --apply` (Claude API, day limit `MONTHLY_USD`, default 30), Find more (things to do, markets) queued for `MONTHLY_FIND` (default ca-la-kimberly; the running worker does them, the suggestions wait 14 days in the editor), then one report saved in the database (`events`, kind `monthly_report`) and emailed through Resend (`RESEND_API_KEY`, `REPORT_EMAIL` in the env file). Tests: `--dry-run` (nothing written, queued or saved), `--steps check,events,find`, `--email` (send even in a dry run): `node worker/monthly.mjs --dry-run --steps find --email` asks Google and Claude nothing. By hand on the server: `systemctl start guide-worker-monthly`; its log: `journalctl -u guide-worker-monthly`. It replaces the desktop task "Monthly check of every live guide" (paused 28 Oct 2026).

## A guide's folder and its database row: pull and push
The database is the live guide (decided 23 Oct 2026, docs/plan-ca-la-kimberly-on-product.md). To work on a guide as files:
- `npm run guide:pull -- <site>`: the live guide into `sites/<site>` (content, i18n, private Wi-Fi, site.json, theme.css). Only changed files are rewritten, in their own key order and indentation.
- `npm run guide:push -- <site>`: content check, then images (public/, only new or changed) and the guide to its row. Refused if the guide changed in the database (editor, monthly check) since the last pull: pull first, or `--force`. Refused while the editor has changes not published yet (`guides.draft`): publish or undo them in the editor, or `--drop-draft`. A new guide needs `--owner-email <email>`. `guide:pull` says when such changes exist (it pulls the live guide, without them).
A guide keeps its own storage key (Ca La Kimberly: clk), so guests' saved settings survive. The sync state is in `sites/<site>/private/.synced.json` (git-ignored).

## Monthly place check for published guides
`npm run check-guides` (dry run, report only) and `npm run check-guides -- --apply` (save the fixes). Options: `--slug <slug>` for one guide, `--days 0` to re-check recent places too.
For every place in a published host guide (markets, things to do, the host's bars and restaurants) it asks Google Places once: still open, exact Google Maps listing, opening hours. Each place keeps its Google id and a "checked" date, so a place checked in the last 25 days costs nothing. Not run on builds (cost): the monthly scheduled task runs it, and it can be run by hand after new research or host edits.
Rules: official hours (a place with a source url and a schedule) are compared, never replaced; permanently closed places are removed; temporarily closed ones get "check" (often the off-season); a Google answer that does not share a real word with the place's name, or is not the listing the guide already links to, is left for a human. Hand-made guides (Ca La Kimberly) are skipped: use `npm run check-places -- <site>` on their folder.
Needs GOOGLE_PLACES_KEY in Guest Guides/.env as well as the worker's key.
